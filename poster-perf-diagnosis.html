P0-1 网络请求：ffprobe 同步串行阻塞

P0 网络请求 main.py:1493

根因

main.py 第 1493 行：_collect_poster_items() 在收集每个视频时同步调用 _probe_video_duration()，该函数通过 subprocess.run() fork ffprobe 子进程。N 个视频 = N 次串行进程调用，每次约 0.1-0.3s。FastAPI 的同步路由在线程池中执行，但该函数本身是 CPU/IO 密集阻塞，30 个视频约需 5s。

影响

高 — 首次加载 /api/poster 阻塞 3-8s（取决于视频数量），浏览器在 API 返回前无法渲染任何内容（仅有骨架屏闪烁）。后续 60s 内有缓存命中，但首次体验极差。

方案：时长探测改为后台异步 + 返回时降级

API 首次返回时 duration 为 null，前端立即渲染。后端启动后台线程批量并行探测，写入持久化缓存（JSON 文件）。前端通过轮询或 SSE 获取补充数据。已有 _duration_cache 机制，只需解耦探测时机。

# main.py 修改：_collect_poster_items 不再同步探测
def _collect_poster_items(download_root, folder=None):
    cache_key = _scan_key(download_root, folder)
    cached = _scan_cache_get(cache_key)
    if cached is not None:
        return list(cached.get("items", []))

    # ... 收集 items（同原逻辑）...
    for item in items:
        built = _build_poster_item(name, item)
        # 从持久化缓存读取，不阻塞
        built["duration"] = _load_duration_from_cache(built["video"], built["folder"])
        items.append(built)

    # 后台异步探测缺失的时长（非阻塞）
    missing = [i for i in items if not i["duration"]]
    if missing:
        threading.Thread(target=_batch_probe_durations,
                         args=(download_root, missing), daemon=True).start()

    items.sort(key=lambda x: (x["folder"], x["stem"]))
    _scan_cache_set(cache_key, {"items": items})
    return items

def _batch_probe_durations(root, items):

P0-2 图片压缩：缩略图直传原图

P0 图片资源压缩 main.py:1516

根因

main.py 第 1529 行：api_thumb() 直接返回 FileResponse(str(resolved))，将原始图片文件（可能 2-8MB 的 JPEG/PNG）作为缩略图传输。海报墙卡片尺寸仅 200×113px，但加载的是 1920×1080 甚至更大的原图。无 resize、无 WebP 转换、无质量压缩。

影响

高 — 每页 10-30 张缩略图，原图每张 1-5MB，总带宽 10-150MB。即使懒加载，首屏 10 张图也需 10-50MB，弱网下加载 5-30s。

方案：后端动态生成缩略图 + 缓存到磁盘

# main.py 新增：缩略图生成器（依赖 Pillow）
from PIL import Image
import io, hashlib

THUMB_CACHE_DIR = Path(".thumb_cache")
THUMB_CACHE_DIR.mkdir(exist_ok=True)
THUMB_SIZE = (320, 180)  # 16:9, 2x 显示尺寸

def get_or_create_thumb(source_path):
    # 缓存键：源文件 mtime + 路径 hash
    key = hashlib.md5(f"{source_path.stat().st_mtime_ns}::{source_path}".encode()).hexdigest()[:12]
    cache_file = THUMB_CACHE_DIR / f"{key}.webp"
    if cache_file.exists():
        return cache_file
    # 生成缩略图
    img = Image.open(source_path)
    img.thumbnail(THUMB_SIZE, Image.LANCZOS)
    img.save(cache_file, "WEBP", quality=80)
    return cache_file

@app.get("/api/poster-thumb")
def api_thumb(folder="", name=""):
    # ... 安全校验同原逻辑 ...
    thumb_path = get_or_create_thumb(resolved)
    return FileResponse(str(thumb_path), media_type="image/webp",
                         headers={"Cache-Control": "public, max-age=86400"})

预期效果：缩略图从 1-5MB 降至 10-30KB（WebP），带宽降低 50-100 倍，首屏图片加载 <0.5s。

P0-3 缓存策略：静态资源无缓存头

P0 缓存策略 main.py:1529,1547

根因

所有 FileResponse 调用均未设置 HTTP 缓存头。浏览器对 /api/poster-thumb 和 /api/poster-video 的响应默认不缓存（无 Cache-Control、ETag、Last-Modified），每次页面刷新都重新下载所有缩略图和视频元数据。CSS 文件 design-system.css 同样无缓存头。

影响

高 — 每次刷新重复下载 10-50MB 缩略图，即使内容未变。二次访问体验等同首次。

方案：为静态资源添加长缓存头 + 文件指纹

# 方案 A：FastAPI 中间件统一添加缓存头
@app.middleware("http")
async def add_cache_headers(request, call_next):
    response = await call_next(request)
    if request.url.path.startswith("/static/"):
        response.headers["Cache-Control"] = "public, max-age=31536000, immutable"
    elif request.url.path.startswith("/api/poster-thumb"):
        response.headers["Cache-Control"] = "public, max-age=86400"
        response.headers["Vary"] = "Accept-Encoding"
    elif request.url.path.startswith("/api/poster-video"):
        response.headers["Cache-Control"] = "public, max-age=3600"
    return response

# 方案 B：CSS 文件名加版本指纹（推荐）
<link rel="stylesheet" href="/static/css/design-system.css?v=20260710" />
# 或构建时生成 hash：design-system.a1b2c3.css

预期效果：二次访问缩略图 0 字节传输（304/缓存命中），CSS 永久缓存。视频文件 1 小时缓存。

P1-1 JS 执行：全量重渲染 + 重复时长探测

P1 JavaScript 执行效率 poster.html:210,239

根因

问题 1（第 210 行）：toggleSelect(k) 调用 renderGrid()，导致每次勾选/取消勾选一个复选框就全量重建整个网格 DOM（innerHTML 字符串拼接 + 解析）。10-30 张卡片的 DOM 节点全部销毁重建。

问题 2（第 239-246 行）：scheduleDP() 在前端创建 <video> 元素加载视频元数据来探测时长，与后端 ffprobe 完全重复。每页 10-30 个 video 元素，消耗大量内存和网络（虽仅 metadata，仍需请求视频头）。

影响

中 — 勾选操作有明显卡顿（10-30ms 重渲染 + GC），批量勾选时累积。客户端时长探测产生 10-30 个额外网络请求和视频解码。

方案 1：toggleSelect 改为 DOM 局部更新

// poster.html 修改
function toggleSelect(k) {
    if (selectedKeys.has(k)) selectedKeys.delete(k);
    else selectedKeys.add(k);
    // 只更新该卡片的选中态，不重渲染整个网格
    const card = document.querySelector(`.mcard[data-key="${CSS.escape(k)}"]`);
    if (card) {
        card.classList.toggle('sel', selectedKeys.has(k));
        const cb = card.querySelector('.msel');
        if (cb) cb.checked = selectedKeys.has(k);
    }
    updateST();  // 只更新状态栏数字
}

renderGrid 中卡片添加 data-key 属性以支持查找。

方案 2：移除客户端时长探测，依赖后端异步补充

// 删除 scheduleDP / runDP 函数，改为轮询后端
async function pollDurations() {
    const fv = document.getElementById('folderFilter').value;
    const r = await fetch('/api/poster/durations?folder=' + encodeURIComponent(fv));
    const d = await r.json();
    if (d.ok) {
        Object.entries(d.durations).forEach(([k, v]) => {
            durationCache.set(k, v);
            updateDK(k, v);
        });
    }
}
// 首次加载后轮询一次，5 秒后再轮询一次（覆盖后台探测完成的）
setTimeout(pollDurations, 2000);
setTimeout(pollDurations, 6000);

预期效果：勾选操作从 10-30ms 降至 <1ms，消除 10-30 个 video 元素的内存和网络开销。

P1-2 CSS 优化：全站样式未压缩未拆分

P1 CSS 优化 design-system.css

根因

design-system.css 共 471 行，包含全站所有页面的样式（topbar、tab-nav、strip、blogger、drawer、log-panel、waterfall 等），但 poster.html 仅使用其中约 30%（reset、shell、hero、toolbar、mgrid、mcard、modal、pagination、skeleton、buttons、forms）。未压缩、未 minify、无 gzip。

影响

中 — 额外传输 ~8KB 未使用 CSS，解析和构建 CSSOM 也有开销。虽不是主要瓶颈，但叠加渲染阻塞效应。

P1-3 渲染阻塞：CSS 同步加载无预加载

P1 渲染阻塞 poster.html:7

根因

poster.html 第 7 行：<link rel="stylesheet"> 在 <head> 中同步加载，浏览器必须下载并解析 CSS 后才渲染任何内容。无 preload 提示，无 preconnect 到 API 源。

影响

中 — 首次白屏时间增加约 0.2-0.5s（CSS 下载 + 解析）。虽然 JS 在 body 底部不阻塞，但 CSS 阻塞首屏。

方案：资源预加载提示

<head>
  <!-- 预连接 API 源，减少 TCP/TLS 握手延迟 -->
  <link rel="preconnect" href="/api">
  <!-- 预加载 API 请求（最高优先级） -->
  <link rel="preload" as="fetch" href="/api/poster" crossorigin>
  <!-- 关键 CSS 内联（见 P1-2） -->
</head>

预期效果：API 请求与 CSS 下载并行，减少 0.3-0.5s 串行等待。

P2-1 资源大小：内联 SVG 重复 + 无 gzip

P2 资源文件大小 poster.html:14,98

根因

SVG 图标内联在 HTML 中（返回箭头第 14 行、关闭按钮第 98 行、播放按钮第 196 行），每张卡片的播放按钮 SVG 重复内联。HTML 文件约 8KB 未压缩。后端未启用 gzip/brotli 压缩。

低 — 8KB 在现代网络下影响极小，但 gzip 后可降至 ~2KB。

P2-2 DOM 复杂度：innerHTML 全量替换

P2 DOM 结构复杂度 poster.html:190

根因

renderGrid()（第 190 行） 使用 innerHTML = pi.map(...).join('') 全量重建网格。每张卡片约 8 层 DOM 嵌套（article > input + div.mcv > img + div.mplay + div.mdur + div.mbd > div.mnm + div.mmt + div.mac）。分页限制了单次渲染数量（10-30），影响可控。

影响

低 — 分页机制将单次 DOM 节点限制在 ~300 个，现代浏览器可轻松处理。主要问题是与 P1-1 叠加的交互重渲染。

方案：DocumentFragment 增量构建（可选优化）

// 使用 DocumentFragment 替代 innerHTML 字符串拼接
function renderGrid() {
    const g = document.getElementById('grid');
    g.innerHTML = '';  // 一次性清空
    const frag = document.createDocumentFragment();
    for (const i of getCPI()) {
        const card = createCardElement(i);  // 返回 DOM 元素
        frag.appendChild(card);
    }
    g.appendChild(frag);  // 一次性插入
}
// 或使用模板元素 <template> 克隆，避免字符串解析开销

预期效果：DOM 构建从字符串解析改为元素克隆，减少 10-20% 构建时间。优先级最低。
